# Risk model data intake

## What is already here

`vendor_risk_training_data.csv`, `vendor_risk_train.csv`, `vendor_risk_validation.csv`,
and `vendor_risk_test.csv` are generated from `app.model.generate_training_data()`. Their
targets are generated by `_synthetic_label()`, which encodes hand-written scoring rules.
They are useful for exercising the pipeline and checking that it can learn those rules.
They are not historical supplier outcomes and must not be presented as evidence of
real-world predictive accuracy.

## Collecting observed outcomes

Use `observed_supplier_outcomes_template.csv` as the intake shape. Each row is one
supplier's feature snapshot at `snapshot_at`; all feature values must have been available
on that date. The event-label columns record whether a *confirmed* event occurred during
the following 180 days. A value of `0` means the complete 180-day follow-up was observed
with no such event; unknown or incomplete follow-up must be blank, never zero.

Keep evidence references in `label_evidence_ref` (for example an internal incident,
delivery, recall, or audit ID). Do not put patient data, personal contact details, or free
text with sensitive information in this training file. Preserve the underlying records in
the system of record and use a stable pseudonymous `vendor_id`.

Important: `spend_risk` is an internal model dimension, not a standard observed event. For
now its target is specifically `spend_integrity_event_180d` (a confirmed invoice/spend
integrity issue), not ordinary spend variation. Revisit the dimension mapping before
training if that is not the intended business outcome.

## Potential external quality-event source

CDSCO publishes monthly Not of Standard Quality (NSQ) alerts with product, batch,
manufacturer, and test-result information. These are useful external quality signals and
can be linked to a supplier/product record after careful entity resolution. They are not
complete negative labels: no alert does not prove a manufacturer or batch had no quality
issues. Do not use “not in alert list” as a negative training label.

- CDSCO alerts: https://cdsco.gov.in/opencms/opencms/en/Notifications/Alerts
- CDSCO sample April 2025 NSQ report:
  https://cdsco.gov.in/opencms/resources/UploadCDSCOWeb/2018/UploadAlertsFiles/CDSCO%20NSQ%20ALERT%20FOR%20THE%20MONTH%20OF%20APRIL-2025.pdf
- Government eProcurement portal (tender context, not fulfillment performance):
  https://www.etenders.gov.in/

### Extracted source data

`cdsco_nsq_2025_04.csv` contains the 60 batch-level entries in the CDSCO/Central
Laboratories April 2025 NSQ report. It is transcribed into a tidy CSV with the report row,
product, batch, named manufacturer, importer when the report provides one, test finding,
lab, report month, and source URL. Repeated batches from one manufacturer remain separate
rows because they are separate reported batch findings. Product and company names are kept
as report text rather than resolved to this project's vendor IDs.

These are real, publicly reported positive quality findings. They are not a balanced
supplier-performance dataset and do not include confirmed clean batches, delivery history,
or the feature snapshots required to retrain the six-dimension risk model. Use the file
for provenance-aware external quality evidence or demonstrations of data ingestion, not as
standalone training/validation data. Batch strings are transcribed from the report; verify
against the PDF before using them for a regulatory action.

## Before fitting a production model

1. Obtain supplier master, PO line, goods-received, quality, invoice/dispute, compliance,
   and incident records from the organization's ERP/QMS/WMS. Public sources cannot supply
   the organization's delivery performance or dispute outcomes.
2. Resolve manufacturer, distributor, and contracted supplier as separate entities. A
   manufacturer recall must not automatically be attributed to every distributor.
3. Link each label to dated source evidence, check follow-up completeness, and prevent
   post-snapshot information from entering features.
4. Split evaluation by time (and report supplier overlap); compare against a simple,
   transparent baseline. Report event prevalence, precision/recall, PR-AUC, calibration,
   and confidence intervals per outcome. Rare outcomes may not support fitting yet.
5. Keep the artifact in offline/shadow evaluation until a domain owner reviews errors and
   the validation protocol. Never promote on synthetic metrics or a tag alone.

No model was retrained from the existing generated files in this work: doing so would
reproduce the same synthetic target and add no evidence about real outcomes.

## Running the learning project without real history

The service uses the archived project baseline whenever no validated observed-outcome
model is registered. API responses and the Risk Intelligence UI identify its synthetic
provenance. The project approval flow consumes its scores so the end-to-end workflow can
be presented, while the UI makes clear that synthetic metrics are not real-world accuracy.
