    Frequently Asked Questions (FAQ)

    1. Can I run MediSource AI without an internet connection or Groq API key?

    Yes. MediSource AI is architected with a two-tier extraction engine: - If GROQ_API_KEY is provided, the platform uses Groq LLMs (llama3-70b-8192 or mixtral-8x7b-32768) for deep semantic extraction and intelligent fraud screening. - If GROQ_API_KEY is left blank or the network is offline, the service automatically falls back to an offline rule-based pipeline (OpenCV preprocessing, PaddleOCR, regex pattern extractors, and arithmetic consistency verifications). The entire stack runs end-to-end inside Docker without any external API calls.

    2. Why use Apache Kafka instead of direct REST calls between services?

    Healthcare procurement involves multiple cascading side-effects that should not block or fail user transactions: - When an invoice is processed, vendor_intelligence links the document, approval_workflow initiates approval tracking, and risk_intelligence updates behavioral metrics. - Using Kafka guarantees: - Service Decoupling: Services can restart or scale without cascading outages. - Idempotency: Message keys (e.g. document_id, request_id) ensure redelivery does not produce duplicate orders or double-counted spend. - Auditability: Every supply chain state transition is preserved in an immutable event log.

    3. What happens if a scanned medical invoice has poor image quality or low OCR confidence?

    The platform enforces a safety threshold (REVIEW_CONFIDENCE_THRESHOLD = 0.75): - Any document with an overall confidence score below 75% or with active fraud flags is given a status of needs_review. - It will not trigger an automated purchase request. - It is placed in the review queue (GET /api/documents?status=needs_review), where hospital staff can view the original image in MinIO, correct the extracted fields, and approve the document. Approving emits a documents.reviewed event to proceed safely.

    4. How does Open Policy Agent (OPA) decide the approval routing chain?

    Approval chains are dynamically constructed by evaluating three vectors in policies/opa/approval_rules.rego: 1. Total Spend: Small purchases (< ₹50,000) require only Department Manager sign-off; high-value purchases (> ₹2,000,000) require Department Manager, Finance Manager, and Procurement Director. 2. Department: Clinical departments (e.g., Cardiology, Oncology) require departmental head sign-off. 3. Real-time Vendor Risk Tier: High-risk vendors automatically trigger an extra compliance review step, regardless of spend amount.

    5. How does the system handle cold-chain requirements for vaccines and biologics?

    Stock items can be marked with cold_chain: true: - When reserving stock, inventory_intelligence verifies that the warehouse location has active cold-chain compliance and that batch expiry dates are safely in the future. - The system prohibits splitting a cold-chain order across different incompatible storage batches. - If inventory is insufficient, the system records an atomic backorder hold and issues an alert to procurement.

    6. Do I need to host OpenSign to test the digital contract e-signature flow?

    No. While contract_intelligence is equipped to send real HTTP requests to an active OpenSign instance (OPENSIGN_BASE_URL), it contains an internal mock envelope simulator: - If OPENSIGN_BASE_URL is unreachable or unset, the service generates a simulated signature envelope and dispatches the signed webhook callback internally. - This allows the entire demo flow — from purchase approval to contract generation and signed archive — to complete without spinning up a separate MongoDB/Parse-Server stack.

    7. How are database migrations managed across microservices?

    MediSource AI follows a database-per-service model: - Each service contains an Alembic migration tree under services/<service>/alembic/. - On startup, each container invokes app/schema_bootstrap.py, which inspects the local database, automatically applies any pending Alembic revisions, or stamps the baseline for legacy databases. No manual migration commands are required during development.

    8. How do I build and preview this MkDocs documentation site?

    You can preview the documentation locally with hot-reloading: 

    python -m mkdocs serve
    Then visit http://localhost:8000.

    To build the static HTML site for production deployment (e.g., GitHub Pages, S3, or Nginx): 

    python -m mkdocs build
    The compiled HTML and assets will be output to the site/ directory.
