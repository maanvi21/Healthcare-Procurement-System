# Architecture

## Style

Database-per-service microservices, integrated through a Kafka event backbone and fronted
by a single Nginx API gateway. Each service owns its own PostgreSQL database and exposes a
FastAPI REST API. Synchronous calls (gateway → service) are used for request/response UI
interactions; Kafka events are used for cross-service side effects (e.g. an approved
procurement request triggering contract generation and inventory reservation without those
services being directly coupled to `approval_workflow`).

```
                                   ┌────────────────────────┐
                                   │   React + Bootstrap     │
                                   │   frontend (SPA)        │
                                   └────────────┬────────────┘
                                                 │ HTTP
                                   ┌────────────▼────────────┐
                                   │   Nginx API Gateway      │
                                   │   /api/documents  ──────┼──► document_intelligence :8001
                                   │   /api/vendors    ──────┼──► vendor_intelligence   :8002
                                   │   /api/approvals  ──────┼──► approval_workflow     :8003
                                   │   /api/inventory  ──────┼──► inventory_intelligence:8004
                                   │   /api/contracts  ──────┼──► contract_intelligence :8005
                                   │   /api/risk       ──────┼──► risk_intelligence     :8006
                                   └───────────────────────────┘

  document_intelligence ──┐                                   ┌── contract_intelligence
  vendor_intelligence ────┤                                   ├── risk_intelligence
  approval_workflow ──────┼──────────►  Kafka  ◄───────────────┤
  inventory_intelligence ─┘         (event backbone)           └──

  Shared infra: PostgreSQL (db-per-service), Redis (locks/dedup), MinIO (documents/
  contracts object storage), Open Policy Agent (approval + compliance rules as code),
  Temporal (long-running approval workflows: reminders, timeouts, escalation), MLflow
  (risk-model experiment tracking).
```

## Services

### document_intelligence (Team A) — port 8001
Ingests documents (upload, and stubs for email/API/shared-folder intake), stores originals
in MinIO, runs PaddleOCR + OpenCV preprocessing, classifies the document type, extracts
structured fields, screens for fraud, computes per-field confidence, flags duplicates by
content hash + vendor/invoice-number match, and exposes a manual-review queue for
low-confidence or flagged documents.
Publishes `documents.ingested`, `documents.processed`, `documents.reviewed`.

**Two-tier intelligence, LLM-first with a deterministic fallback.** Classification
(`app/classification.py`), field extraction (`app/extraction.py`) and fraud screening
(`app/fraud.py`) each try a Groq LLM pass (`app/llm_extractor.py`) and fall back to a
rule-based baseline — keyword scoring, regex patterns and arithmetic consistency checks —
whenever `GROQ_API_KEY` is unset, the model is unreachable, or the response will not parse
as JSON. Consequences of that design:

- The service runs end to end with **no API key and no network**, which is what keeps the
  `docker-compose` demo self-contained. Set a key to get the accuracy lift.
- The two engines **compose rather than compete**: LLM-extracted fields take precedence,
  and regex backfills anything the model returned null for (it reliably catches labelled
  patterns like GSTIN and drug-licence numbers that the prompt does not ask for). Fraud
  flags are the union of both engines' findings and the score is the max of the two.
- Every document records which engine ran (`documents.extraction_engine`) and its
  per-stage confidences and fraud flags (`documents.extraction_notes`), so an extraction
  can always be audited after the fact.

Fraud screening is genuinely two-layer: deterministic arithmetic (line items that do not
sum to the stated total, tax exceeding total, missing vendor) always runs and needs no
model, while the LLM pass adds the judgement calls a regex cannot make — implausible unit
pricing for a medical item, suspicious vendor details, malformed batch/licence numbers.

### The document → vendor → approval handoff

The three services above are joined by one chain, and each link fails soft:

1. **Name → id.** `document_intelligence` extracts a vendor *name*; everything downstream
   keys off a vendor *id*. On ingest it calls `GET /vendors/resolve` on
   `vendor_intelligence`, which matches exact-then-fuzzy and returns `{vendor_id: null}`
   rather than guessing when the match is ambiguous. Attaching an invoice to the wrong
   supplier is much worse than leaving it unattached, so an unresolved document routes to
   the review queue, where correcting the vendor name re-runs resolution.
2. **Document → vendor profile.** `vendor_intelligence` consumes `documents.processed` /
   `documents.reviewed` and files the document against the vendor (`vendor_documents`),
   so compliance certificates and invoices accumulate on a supplier's profile
   automatically. The write is idempotent — redelivery cannot duplicate a link.
3. **Document → procurement request.** `approval_workflow` consumes the same events and
   raises a `ProcurementRequest`, which then follows the ordinary OPA → Temporal →
   approver-chain path. Because this creates work for humans without a human asking, the
   gate is strict: invoices and POs only, `extracted` or `validated` only (never
   `needs_review`), a resolved vendor, and a positive parseable total. Idempotency is
   enforced by a unique `source_document_id` on the request.

A document that fails any gate is not lost — it waits in the review queue, and the
`documents.reviewed` event re-runs the same checks once a human has corrected it.

### vendor_intelligence (Team A) — port 8002
Vendor master data for medical suppliers, pharma distributors and biomedical AMC
contractors. Onboarding validates drug-license number format/expiry, an FDA/CDSCO-style
registration ID, GST number, and a sanctions/watchlist stub check; produces an
approve/reject/manual-review outcome. Publishes `vendor.onboarded`, `vendor.updated`.

### approval_workflow (Team B) — port 8003
Evaluates OPA `approval_rules.rego` (spend threshold × department × vendor risk band) to
pick the approver chain, starts a Temporal workflow (`ApprovalWorkflow`) that waits for a
signal (approve/reject) with a timeout, escalates to the next approver on timeout, and
records full history. The `vendor_risk_band` OPA routes on is fetched from
`risk_intelligence` (`app/risk_client.py`) whenever the caller does not supply one — the
rego tests the band *before* any spend threshold, so leaving it unset silently gave a
high-risk vendor the short chain. An explicit band from the caller still wins, and an
unreachable or never-assessed vendor routes on spend alone rather than being assumed low. Redis is used to de-duplicate concurrent submissions of the same
request. Publishes `approval.requested`, `approval.approved`, `approval.rejected`,
`approval.escalated`.

### inventory_intelligence (Team B) — port 8004
Tracks ward/pharmacy stock by SKU + batch + expiry date. On a procurement request, checks
availability, reserves stock with a Redis lock (preventing double-reservation across
concurrent requests), releases expired reservations via a background sweep, and raises
backorder/reorder suggestions for shortfalls — cold-chain items are never partially
reserved across incompatible batches. Publishes `inventory.reserved`, `inventory.backorder`.

### contract_intelligence (Team C) — port 8005
Jinja2 contract templates (Supply Agreement, Biomedical Equipment AMC, Vendor Agreement,
NDA) populated from approved procurement + vendor data, stored in MinIO, sent through an
OpenSign-compatible e-signature client (real HTTP integration, pointed at a self-hosted
OpenSign instance via `OPENSIGN_BASE_URL`), with version/renewal/expiry tracking in
Postgres. Publishes `contract.generated`, `contract.signed`.

### risk_intelligence (Team C) — port 8006
Scores **six** risk dimensions — compliance, fraud, financial, supplier, **spend** and
operational — with a scikit-learn gradient-boosted multi-output regressor over 17 features,
plus **unsupervised anomaly detection** alongside them. Training runs are logged to MLflow
(params, metrics, model artifact); inference loads the latest `Production`-stage model.
Publishes `risk.assessed`.

**Measured, not assumed.** The service keeps a `vendor_observations` table fed from
`documents.processed` / `documents.reviewed` and `procurement.request.created`, and
`app/analytics.py` derives features from it: observed fraud-flag rate and mean fraud score
(carried over from document_intelligence's own screen), duplicate-invoice rate, spend
volatility, spend growth, invoice-amount z-scores, round-amount rate, and a late-delivery
rate measured by matching delivery notes against their purchase orders. This replaced a
set of hardcoded constants — five of the original eight features were fixed numbers, which
meant a published "risk band" was in practice a restatement of the vendor's licence expiry
date. That mattered because `approval_workflow` feeds `vendor_risk_band` into OPA routing,
so an unearned "low" could shorten a real approval chain.

Two signals remain caller-supplied by design — cold-chain violations and financial health.
No service in this build owns cold-chain telemetry or vendor financial statements, and
deriving them from procurement data would be fabrication; they stay as explicit API inputs
for a WMS/ERP integration to provide. A vendor with too little history falls back to
documented cold-start defaults, and every assessment records `observation_count` and
`is_cold_start` so a consumer can tell an estimate from a measurement.

**Anomaly detection** (`app/anomaly.py`) is deliberately separate from the supervised
dimensions: those score a vendor against patterns someone anticipated when the labels were
written, whereas anomaly detection asks whether a vendor is behaving unlike itself or
unlike its peers, and so can surface a novel pattern for which every individual risk score
looks unremarkable. An IsolationForest over the vendor's own invoice history is paired with
explicit named rules (sudden spend spike, invoice far outside peer norms, burst of invoices
in a short window) because a bare score nobody can interpret is not actionable in a
procurement review — flagged vendors surface at `GET /risk/anomalies` with reasons.

Re-assessment is debounced per vendor, **leading and trailing**. An assessment loads the
MLflow model and calls vendor_intelligence, so a burst of documents must not trigger one
per event; but a leading-only debounce would score the first invoice of a burst and drop
the rest, leaving exactly the burst that anomaly detection exists to catch unscored. Events
arriving inside the window mark the vendor dirty and a flusher re-scores once it closes.

## Cross-cutting

- **Kafka** topics are declared in `scripts/init-kafka-topics.sh` and documented in
  `SCHEMA.md`. Each service ships both a producer and (where relevant) a consumer.
- **OPA** policies live in `policies/opa/` and are loaded into the `opa` container at
  startup; services call `POST http://opa:8181/v1/data/...` for a decision.
- **Schema migrations** run at service startup (`app/schema_bootstrap.py`): fresh
  databases are built by Alembic, and databases created by the earlier `create_all` path
  are adopted by stamping the baseline first. `create_all` remains only as a loud
  last-resort fallback if Alembic cannot run at all.
- **Temporal** worker for `approval_workflow` runs as a second process
  (`temporal_worker.py`) alongside the FastAPI app in the same container.
- **MinIO** buckets: `documents`, `contracts` (created by `scripts/deploy.sh`).
- **Auth**: out of scope for this build (documented as a follow-up — a real deployment
  would put OAuth2/OIDC at the Nginx gateway); demo endpoints are unauthenticated.

## Explicitly deferred (see README "Scoping notes")

- Apache Spark distributed document processing — single-node OCR is sufficient at demo
  scale; the extraction pipeline is stateless per document so horizontal scaling by running
  more `document_intelligence` replicas covers realistic load before Spark would be needed.
- Label Studio — offline OCR/extraction model QA tool, not part of the deployed runtime.
- Full Team-D platform stack (Prometheus/Grafana/Loki, GitLab CE/Jenkins CI-CD, OpenBao,
  Terraform/Ansible, OpenProject) — only the "minimal deploy layer" was requested: compose
  + k8s manifests + migrations + `/health` endpoints on every service.
